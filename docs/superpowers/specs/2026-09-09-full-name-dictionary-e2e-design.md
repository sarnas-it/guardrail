# Дизайн: словарная детекция ФИО + расширенный e2e-корпус

## Цель

Расширить guardrail двумя связанными возможностями:

1. **Детекция ФИО (ПДн)** словарным методом: не regex, а справочники фамилий/имён/отчеств, подключаемые файлами, с оконным подсчётом «≥ min_matches разных категорий в соседних токенах» и файлом исключений для гашения ложных срабатываний.
2. **Локальный e2e-тест** (`go test ./e2e/`): реальные git-репозитории с утечками по всем правилам guardrail (секреты и ПДн), сверка фактического набора `ruleID` с ожидаемым — без Docker и GitHub.

Пользовательский флоу: правилo `full_name_ru` (warn), работает только когда в `guardrail.yml` подключены файлы словарей; битый подключённый файл → exit 2; пустая/отсутствующая секция → правило off без ошибки.

## Решения по требованиям (из диалога)

- ФИО детектируется новым правилом `full_name_ru` (PII, warn). Regex-подход отвергнут.
- Справочники: **без встроенного дефолта** — всё из подключаемых файлов, пути относительны директории `guardrail.yml`.
- Значения в конфиге — строки-пути к файлам, а не массивы (конфиг не засоряется деталями).
- Семантика: скользящее окно соседних токенов; учитывается число **различных категорий** (фамилия/имя/отчество), представленных в окне; порог `full_name min_matches` (2 default / 3).
- Файл исключений: полная нормализованная фраза окна из списка → находка отбрасывается целиком.
- Схема секции: четыре файла `surnames_file`, `given_names_file`, `patronymics_file`, `exclusions_file`.
- Поведение: указанный-но-битый файл → ошибка exit 2; пустая секция / все файлы пусты → правило `full_name_ru` не срабатывает, без ошибки.
- Архитектура детектора: вариант A — отдельный словарный модуль, вызываемый движком отдельно от regex-прохода.

## Правило

В `internal/rules/defaults/pii.yaml` добавляется запись:

```yaml
- id: full_name_ru
  category: pii
  severity: warn
  description: Russian full name (surname + given name + patronymic)
  type: dictionary
```

## Схема данных

### Правила (`internal/rules`)

- В `Rule` и `fileRule` добавляется поле `Type string` (`yaml:"type"`), значения: `regex` (default) или `dictionary`.
- Валидатор:
  - `type: dictionary` → не допускаются поля `regex`, `keywords`, `entropy_min` (иначе ошибка загрузки).
  - `type: regex` (включая пустое) → ведёт себя как сейчас.
- `internal/rules` не хранит сами словари — только метку типа.

### Пакет `internal/names` (новый)

```go
type Categories int
const (
    Surname Categories = 1 << iota
    GivenName
    Patronymic
)

type Set struct {
    surnames, givenNames, patronymics map[string]struct{}
    exclusions map[string]struct{}
    MinMatches int
    Window     int
    active     bool
}

func Load(configPath string, cfg *config.Config) (*Set, error)
func (s *Set) Active() bool
func (s *Set) Classify(token string) Categories
func (s *Set) IsExcluded(phrase string) bool
```

- `Load` читает файлы из `cfg.Names` относительно директории `configPath`.
- Формат файла: одна запись на строку. Нормализация: нижний регистр (`unicode.ToLower`), только буквы; пробелы допустимы только внутри фраз `exclusions_file`.
- Битый/нечитаемый указанный файл → ошибка (exit 2).
- Если секция отсутствует или все файлы пусты → `active = false`.
- `exclusions_file` опционален (отсутствие = пустой список исключений).

### Конфиг (`internal/config`)

Добавляется `NamesConfig`:

```yaml
names:
  min_matches: 2             # 2 или 3; default 2
  window: 4                  # >= 2; default 4
  surnames_file: data/surnames.txt
  given_names_file: data/given_names.txt
  patronymics_file: data/patronymics.txt
  exclusions_file: data/exclusions.txt
```

- Поля: `MinMatches int`, `Window int`, `SurnamesFile`, `GivenNamesFile`, `PatronymicsFile`, `ExclusionsFile string`.
- Валидация: `min_matches ∈ {2,3}` (пусто → 2), `window ≥ 2` (пусто → 4). Неизвестный ключ → ошибка (KnownFields, как сейчас).
- `config.Load` читает только пути; сами файлы читает `names.Load` (у него есть директория конфига).

## Алгоритм детекции (Секция 3)

Вход — одна добавленная строка диффа; выход — `[]detect.Match{RuleID: "full_name_ru", Value: <фраза>}`.

1. Токенизация по небуквенным символам (`\p{L}+`), оставляются кириллические токены (включая Ё).
2. Токен нормализуется (нижний регистр) и классифицируется по трём Set → битмаска `S|G|P` (токен может попасть в несколько списков; маски складываются).
3. Скользящее окно размера `window` токенов, шаг 1. Внутри окна учитываются токены с ненулевой маской; служебные слова не обнуляют окно.
4. Подсчёт: число **различных категорий**, представленных в окне = `popcount(union масок)`. Если `>= min_matches` → кандидат.
5. Фраза-кандидат — от первого до последнего токена окна с ненулевой маской (внутренние служебные слова включаются), нормализована в нижний регистр.
6. Если фраза ∈ `exclusions` → кандидат отбрасывается.
7. Схлопывание дубликатов: не более одного `Match` на (строку, фразу).

Пример: `"name": "Иванов Иван Иванович"` → токены `иванов`(S), `иван`(G+S), `иванович`(P) → union = 7, popcount 3 ≥ 2 → кандидат «иванов иван иванович».

## Интеграция в движок (Секция 4)

- `engine.Options` получает новое поле `Names *names.Set` (nil → словарный детектор не запускается).
- `engine.Scan`: для каждой добавленной строки, если `Names != nil && Active()`, вызывается `detect.FullName(line, set)`, результат объединяется с regex-находками `detect.Line` и идёт по общему пути (severity override → allowlist → fingerprint → сортировка).
- `detect.Line` остаётся чистым regex-детектором (сигнатура не меняется).
- Новый файл `internal/detect/fullname.go`:
  ```go
  func FullName(line string, s *names.Set) []Match
  ```
- Fingerprint ФИО считается как обычно: `sha256(ruleID + file + value)`.
- Маскирование и отчёты без изменений: `full_name_ru` — обычный PII-warn.

## e2e-тест (Секция 5)

Файл: `e2e/e2e_test.go` (пакет `e2e`, `go test ./e2e/ -v`). Без Docker и GitHub, используется локальный git и `engine.Scan`.

Сценарии:

1. **Позитивный полный:** git-репо с base-коммитом и коммитом-утечкой, содержащим образцы по всем правилам; временный `guardrail.yml` + словари; сверка множества фактических `RuleID` с ожидаемым и severity (секреты block, ПДн warn).
   - Ожидаемый набор: aws_access_key, google_api_key, github_token, slack_token, telegram_bot_token, private_key_pem, jwt_token, db_connection_string, generic_api_key, phone_ru, email, inn_ru, snils_ru, passport_ru, full_name_ru.
2. **Негативный:** похожее-но-не-утечка (`AKIA` без полного ключа, телефон без полного формата, «Анна Каренина» в exclusions) → соответствующих находок нет.
3. **Allowlist:** находка ФИО в allowlist → отсутствует в отчёте, `Result.Allowed` растёт.
4. **Порог ФИО:** `min_matches: 3` не ловит «Иванов Иван» (2 слова), но ловит полное ФИО.
5. **Off без словарей:** секция `names` отсутствует → `full_name_ru` не срабатывает, остальные правила работают.

Корпус образцов утечек — в самом тесте (Go-строки), не отдельные файлы.

## Границы

- ФИО детектируется только построчно (окно не выходит за границы одной добавленной строки диффа).
- Справочники и исключения задаются только файлами через конфиг; встроенных списков нет.
- Отчества/имена/фамилии не дедуплицируются между категориями (токен в нескольких списках — нормально).
- Не добавляются: определение пола, склонение, региональные особенности имён.
- Уже покрыто unit-тестами и не дублируется в e2e: ignore путей (sum/min.js/бинарники), EmptyTree root-commit, SARIF/JSON формат.

## Критерии готовности

- `full_name_ru` появляется в отчётах при подключённых словарях и окне ≥2 разных категорий.
- Файлы словарей/исключений подключаются относительными путями от guardrail.yml; битый файл → exit 2.
- `names` в конфиге валидируется; отсутствие секции не ломает другие правила.
- `go test ./...` зелёный, включая новый `./e2e/`.
- Встроенные regex-правила не регрессировали (существующие тесты проходят).
