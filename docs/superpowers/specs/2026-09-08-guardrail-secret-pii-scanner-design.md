# Дизайн guardrail — сканер секретов и ПДн для CI

## Цель

Продукт Сарнас: container action для GitHub, который при запуске в пайплайне клиентского репозитория локально сканирует изменения PR/push на утечки секретов и персональных данных (ПДн РФ) и блокирует слияние, если в диффе найден секрет. Ничего из репозитория клиента наружу не отправляется.

MVP = публикация action для внешних клиентов: дифф-скан новых изменений, встроенные правила секретов и ПДн РФ, конфиг `guardrail.yml`, вывод «лог + SARIF/JSON», смешанная реакция по типу находки, маскирование значений, без live-валидации ключей.

## Позиционирование

- Кто использует: команды разработки, интегрирующие guardrail в свои GitHub-репозитории.
- Форма поставки: полностью локальный container action (`docker://ghcr.io/sarnas-it/guardrail`).
- Проверки выполняются в окружении клиента; облачный API и дашборд отсутствуют.
- Язык и стек: Go, один бинарь; движок детекции на Git CLI внутри контейнера.

## Репозиторий и структура

Отдельный репозиторий `github.com/sarnas-it/guardrail` (самодостаточный Go-модуль, не подмодуль монорепо sarnas).

## Архитектура движка

Выбранный вариант A: Go-бинарь + `git` в контейнере, дифф через git CLI.

Поток обработки одного файла:

1. `git show head:<path>` → содержимое новой версии файла.
2. `git diff base...head -- <path>` в unified-формате → только добавленные строки (`+`, без `+++`) — это «новое в этом PR».
3. Для каждой добавленной строки прогоняются правила.
4. Находки дедуплицируются по `(rule, path, fingerprint)`.

Переименования, удаления и частичные изменения строк обрабатываются раннером корректно: сканируются только добавленные строки. Бинарные файлы пропускаются (magic + расширение).

### Skip-логика

- Не сканируются бинарные файлы.
- Захардкоженный список исключений: `package-lock.json`, `yarn.lock`, `go.sum` и подобные (шум base64/энтропией). Расширяется конфигом.

## Категории правил и реакция

- **secrets** — `block` (exit≠0): AWS/GCP/Azure keys, GitHub/Slack/Telegram tokens, приватные ключи (PEM/DSA/Ed25519), generic API-ключи (энтропия + сигнатура вида `key=`/`token`), `.env`, строки подключения к БД.
- **pii** — `warn` (exit=0): телефон РФ, email, ИНН, СНИЛС, номер паспорта РФ (две серии).

Механизм правила — композиция трёх проверок (включаются выборочно):

- `regex` — паттерн поиска (RE2).
- `entropy` — порог энтропии Шеннона для generic-ключей.
- `context` — обязательное слово-маркер вокруг матча (`secret`, `password`, `token`, …) для подавления ложных срабатываний.

ПДн-правила по чистому regex дают много FP, поэтому идут с `context`-проверкой и/или `severity: warn`; блокируют всегда только secrets.

## Конфигурация guardrail.yml

```yaml
severity:                     # переопределение реакций по правилам
  aws_access_key: block       # block | warn | off
config:
  ignore:
    paths:
      - "vendor/**"
      - "**/*.min.js"
    matches:                  # обход конкретных срабатываний
      - rule: phone_ru
        path: "internal/tests/fixtures.go"
        fingerprint: "a1b2…"  # хеш контекста строки; либо line: 42
        reason: "тестовые фикстуры"
        until: 2026-12-01     # авто-экспирация allowlist
  scan:
    max_file_size_kb: 512
    extra_ignored_paths: []
  output:
    sarif_file: guardrail.sarif
    reveal: false             # дублирует GUARDRAIL_REVEAL=1
```

Правила настройки:

- Отсутствие `guardrail.yml` не ошибка: работают встроенные правила и дефолты. Ошибка только если файл найден, но не парсится.
- Неизвестный ключ в конфиге — ошибка (защита от опечаток).
- Неизвестное `rule` в allowlist — ошибка с подсказкой ближайшего имени.
- Пути в ignore матчатся от корня репо (glob, gitignore-семантика).
- Пользовательский конфиг не добавляет новых правил — только allowlist и переопределение severity/включения встроенных правил.
- Пустой `max_file_size_kb` означает отсутствие лимита.

## Интерфейс запуска

CLI бинаря (action оборачивает):

```
guardrail scan --base <sha> --head <sha> --config guardrail.yml [--sarif guardrail.sarif] [--json out.json]
```

`action.yml` (container action):

- inputs: `base`, `head` (опциональны), `config` (путь, default корень), `sarif-file` (опционально).
- Если `base` не задан: для PR — SHA базовой ветки из события; для push — родительский коммит head (`git rev-parse head^`). Fallback: если base/merge-base пуст — дифф против пустого дерева (все добавленные строки нового коммита; покрывает первый коммит ветки/репо).
- Контейнер монтирует `$GITHUB_WORKSPACE` в `/github/workspace`.
- GitHub автоматически красит шаг красным при ненулевом exit-коде → PR блокируется.

Локальный запуск для разработки:

```
guardrail scan --base HEAD~1 --head HEAD
guardrail scan --base <branch>
```

## Отчёт и exit-коды

Модель находки:

```go
Finding {
  RuleID      string // "aws_access_key"
  Category    string // "secret" | "pii"
  Severity    string // "block" | "warn"
  File        string
  Line        int
  Value       string // замаскированное значение (если не reveal)
  Fingerprint string // sha256(rule + path + контекст строки)
}
```

Выводы:

1. **Лог (текст):** в конце сводка `N секретов (block), M ПДн (warn), K обходов allowlist`; каждая находка с отметкой `[block]`/`[warn]`, путём:строкой, правилом и замаскированным значением.
2. **SARIF** (по запросу): результат уровня `error`/`warning`, `ruleId`, `location.physicalLocation.artifactLocation.uri`, `region.startLine`, сообщение с правилом и инструкцией.
3. **JSON** (опционально, `--json`): сырая модель находок для скриптов.

Маскирование: значение показывается как `первый 4 символа … последние 4 символа`. Полные значения — только при `GUARDRAIL_REVEAL=1` (env, намеренно не выставляется через `action.yml`). Маскирование включено во всех форматах.

Exit-коды:

- `0` — нет блокирующих находок (ПДн-warn допустимы).
- `1` — есть хотя бы один блокирующий секрет.
- `2` — ошибка выполнения (git-сбой, битый конфиг, пустой head) — пайплайн красный, но это «сломано», не «найдено».

## Границы MVP (сознательно исключено)

- Скан полной истории Git; pre-receive/pre-push hook; live-валидация ключей у провайдеров.
- ПДн не-РФ; номера карт/банковских счетов.
- Веб-дашборд, централизованные политики, мульти-репо агрегация.
- `fail-on`; режим «только новые файлы целиком» — реакция управляется конфигом.
- Пропуск тестов/фикстур по умолчанию без allowlist: тестовые секреты всё равно утечка, решение принимает человек через allowlist.

Критерий готовности MVP: action работает на публичном тестовом репозитории (пример в `examples/`), ловит заранее внесённые секреты и ПДн в PR, allowlist гасит фикстуры, exit-коды корректны, SARIF открывается в GitHub.

## Тестирование

1. Юнит-тесты правил — табличные тесты на каждый встроенный детектор: эталонные секреты/ПДн срабатывают, похожий-но-не-он код молчит; отдельно пороги энтропии (base64 из lock-файлов не даёт secrets-FP).
2. Тесты на git-фикстурах (golden): `testdata/` с готовыми git-репозиториями (коммиты с утечками); запуск `guardrail scan` → сравнение лога/SARIF с `*.golden`.
3. Интеграция allowlist/дедуп: конфиг с `ignore.matches`/`paths` → находка подавлена, fingerprint стабилен, `until` срабатывает.
4. Тест раннера: реальные диффы `base...head` (переименование, удаление, частичное изменение строки, бинарник) — сканируются только добавленные строки, дедуп корректен.
5. E2E GitHub: job в CI собирает образ и запускает action на тестовом репозитории — проверка `action.yml`, монтирования workspace, exit-кодов.
6. Маскирование: reveal off/on, значения из allowlist не печатаются даже при reveal (только hash).

Инструменты: стандартный `go test`, golden-файлы `.golden`, CI — GitHub Actions репозитория guardrail: сборка, `go vet`/lint, юнит+интеграция, публикация образа по тегу.

## Порядок реализации (для будущего плана)
